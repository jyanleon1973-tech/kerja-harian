## 2. 問題点（重要度順）

| 順 | 問題 | なぜ数値が信頼できなくなるか | 修正方針 |
|---|---|---|---|
| 1 | **3D（`world`）座標に依存した指標設計** | BlazePose の world 座標は GHUM 体型モデルへの当てはめで得た「もっともらしい 3D」で、奥行きは単眼回帰、スケールは平均体型に正規化される（腰中点原点、m 単位）。二次情報では 3D 誤差 36-45 mm 程度（未検証）。深い内傾・クローチング・腕とストックの重なりは学習分布外で、骨盤の yaw・z が大きく揺れる。これが 進行方向→ターン判定→外脚/内脚→内傾/外傾/外向 まで連鎖する。 | 指標の一次情報を 2D 画像座標に戻し、撮影方向ごとに「その面で観測できる角度」だけを出す（§5）。3D は補助情報に格下げし、奥行きに依存する値（外向、スタンス幅の cm、骨盤 yaw）は表示しない。 |
| 2 | **cm 表示と 3D 距離の断定**（重心前後/左右、前後差、スタンス幅、股関節高） | world の単位は実寸ではなく正規化体型の m。身長 160 cm と 190 cm の選手で同じ数値が出うる。さらに足底 6 点平均を「板に対する位置」と呼んでいるが、実際の支持面（ブーツソール中心・板）との関係は未知。 | cm を廃止し、足長・下腿長・身長推定値に対する比率（%）と角度で表示。重心は「画像上の姿勢重心（用具なし、推定）」と明記し、信頼度と推定範囲を併記。足圧荷重中心とは別物だと UI で区別。 |
| 3 | **「エッジ角」の名称**（L1104, L1156-1157） | 実体は「すねの左右傾き」。実エッジ角はブーツ・板・雪面の関係で、単眼映像からは測れない。指導現場では最も誤解を招く。 | 名称を「すねの左右傾き（角付けの参考）」に変更し、正面/背面以外では非表示。 |
| 4 | **ターン方向判定が骨盤 yaw の微分** | 骨盤 2 点の 3D 奥行き差から yaw を作り、0.7 s で 4° という小さな閾値で判定。側面撮影では yaw の符号が不定で、L776/L780 の反転ロジックが「左右取り違え」を**検出せず隠す**。ターン判定が誤ると 外脚/内脚・内側/外側 の全指標が反転する。 | 画像上の腰中点の横移動方向、足元→肩の 2D 傾きの符号、板 2D 角の時間変化を組み合わせ、ヒステリシスと最短持続時間（例 0.4 s）を持つ判定に変更。確信度が低いコマは「判定不能」と表示し、ユーザーが手動で指定できるようにする。 |
| 5 | **左右の取り違え対策がない** | BlazePose は側面・背面で左右ラベルが頻繁に入れ替わる。`boneOk` は長さしか見ないので、左右が丸ごと入れ替わった検出は通過する。膝角 L/R、前後差、外脚/内脚ラベルが瞬間的に反転し、時系列がギザギザになる。 | 前コマとの各関節の距離を「そのまま」と「左右入替」で比較し、入替の方が近ければ入替＋フラグ。左右の判定信頼度が低いコマは左右別の指標を非表示にする。 |
| 6 | **補間コマ・平滑化コマが「測定値」として出る** | 0.5 s（15fps で 7 コマ）までの線形補間は切り替え局面の速い動きを消し、補間値でグラフが滑らかに見える。平滑化は補間値も入力にする。 | 補間は描画のみ（破線）にして指標は null。平滑化は検出コマだけで行い、欠落をまたがない。平滑化は One Euro か Savitzky-Golay に置き換え、窓幅を UI に表示。 |
| 7 | **板の線が「足首位置＋固定長」** | 描画は検出線の向きに bbox 高×0.45 の固定長（L902）。実測した tip/tail 長は描画に使われず、`strength` が低くても線が出る（細線）。画像で検出できなくても `skiYaw`・`skiOpen` は骨盤・足向きから計算され「足の向きから推定」と小さく出るだけ。 | 板は「検出できたときだけ、実測した両端まで」描く。未検出なら線もヤウ値も出さない。`skiOpen` は左右とも画像検出があるコマだけ。 |
| 8 | **板検出が古典 CV の勾配方向のみ** | 白い板、ゲート、影、シュプール、雪煙で容易にピークが移る。`measureSkiLen` は「板は雪より暗い」前提（L651, L656）。`fitCamera` の「俯角」は同じモデルの 3D 出力から逆算した循環推定。 | §4 の専用検出器へ移行。それまでは検出の採否を厳しくし、未検出を明示。 |
| 9 | **フレーム時刻と絵の不一致** | `seeked` 3 秒タイムアウトで古い絵を解析する可能性（L323）。`currentTime` は要求値で、実際に提示されたフレームの時刻ではない。iOS の可変フレームレート動画や 120fps スローでは `round(t/dt)` がずれる。 | `requestVideoFrameCallback` の `mediaTime` を各コマに記録し、タイムアウト時はそのコマを「取得失敗」にする。フレーム時刻は等間隔仮定をやめ、記録した時刻で引く。 |
| 10 | **可視度を使わない指標計算** | 描画は visibility<0.3 を省くが、`poseData` は全関節を無条件に使う。隠れた内脚の膝角も確定値で表示される。 | 各指標に「依存関節の最小 visibility」を持たせ、閾値未満なら非表示（または薄字＋信頼度）。 |
| 11 | **`IMAGE` モード＋`latest` URL** | `IMAGE` モードではモデル内部の時間追跡・平滑化が使われず、毎コマ独立検出でジッタが増える。`latest` はモデル更新で結果が黙って変わる。tasks-vision は npm 確認時点で 1.2.0 が最新で、0.10.14 は古い。 | `VIDEO` モード＋単調増加タイムスタンプで検出。モデル URL をバージョン固定（または同リポジトリに同梱、heavy は約 30.7 MB で 100MB 制限内）。 |
| 12 | **鉛直の基準がカメラの Y 軸** | 俯角・斜度の分だけ内傾・前かがみ・すね角がずれる。手動スライダーは再現性がない。 | 撮影方向と「雪面の線（2 点タップ）」または「ストック/ゲートの鉛直」を基準として入力させ、2D 指標をその基準で回転。 |
| 13 | 重心モデルの細部 | 頭が両耳中点、体幹が肩中点起点（de Leva の体幹は胸骨上縁基準）。ブーツ・板・ウェアの質量なし。女性・ジュニアの係数なし。 | 係数の選択肢（性別・年齢）と「用具込み推定範囲」を用意するより、重心そのものを「推定帯」で示す方が誠実。 |

**BlazePose GHUM の 3D の性質**: world landmarks は「腰中点原点・m 単位・y 下向き・z がカメラ方向」の座標で、GHUM 体型モデルの当てはめから回帰された値。単眼で絶対スケールは得られず、骨長の一貫性も保証されない（二次情報）。したがって cm 表示や奥行き差（外向・スタンス幅）の根拠には使えない。

**推奨構成**: 人物検出（RTMDet-nano など Apache 系）→ 簡易追跡（IoU＋速度予測、ユーザー指定 ID）→ RTMPose-m（Halpe26、256×192、fp16 ONNX ≈ 27 MB 推定）→ 関節ごとの信頼度を保持→ 左右入替検査→ 時間フィルタ。実行は onnxruntime-web の `executionProviders:['webgpu','wasm']`（WebGPU は Safari 26 系で対応との情報。公式互換表は未確認）。

## 4. 板・ブーツ検出の選択肢

| 方式 | 構成 | 長所 | 短所 | 学習データの目安 |
|---|---|---|---|---|
| 古典 CV（現状: 勾配方向ヒストグラム＋暗画素長） | JS のみ | モデル不要・軽い | 白い板・影・ゲート・シュプール・雪煙に弱い。「板があるか」を判定できない | 不要 |
| 色・輝度セグメンテーション | 板の色をユーザーがタップ指定→色距離で領域抽出→PCA で主軸 | 自分の板なら安定しやすい | 逆光・反射・雪煙・赤いゲート等で破綻。ブーツは別処理 | 不要（動画ごとに指定） |
| 物体検出 HBB（YOLO/RTMDet） | 板・ブーツ・ストックの矩形 | 実装が容易、ブラウザ事例多数 | 細長い斜めの板は矩形がほぼ無意味で向きが取れない | 1-2k 画像で試作 |
| **回転矩形 OBB**（YOLO11-obb、RTMDet-R） | 板を向き付き矩形で検出 | 向きと長さが直接出る | 事前学習は航空画像（DOTA）なので要ファインチューニング。Ultralytics は AGPL | 1-2k 画像・数千インスタンスで試作、5k 以上で条件横断 |
| インスタンスセグメンテーション（YOLO11-seg、RTMDet-Ins） | マスク→主軸・端点 | 部分隠れに強く tip/tail も得やすい | 重い（yolov8n-seg ONNX 約 14 MB で最軽量クラス）、アノテーションが高コスト | 1-2k 画像（ポリゴン） |
| **キーポイント推定**（RTMPose カスタム、YOLO-pose カスタム） | 身体 17-26 点＋板 tip/binding/tail 各 2-4 点＋ストック 2 点を 1 モデルで | Ski2DPose と同じ発想。板の中心線・ブーツ位置・ストックが骨格と同一座標系で出る | 学習データが必須。板が見えないとき「見えない」と出せる設計が必要（可視フラグ付きで学習） | 2k 画像で試作（Ski2DPose の 1,982 枚と同規模）、5-10k で実用 |

**既製のスキー検出モデル**: Roboflow Universe に「skier_keypoints」（CC BY 4.0、内容説明なし）、「Skiers and Snowboarders」（YOLOv8 チェックポイント、ライセンス未確認）、「Ski detection」（クラス skier、CC BY 4.0、4 年前）、「crossed-skis detection」が見つかったが、**板・ブーツを汎用に検出できる文書化済みモデルは見つからなかった**。学術データでは EPFL の Ski2DPose（1,982 枚、24 点＝身体 16＋ストック 2＋板 8、CC 動画由来）が板の点を含む唯一の公開データ。利用条件はサイトに到達できず未確認。Ski-PosePTZ（GS、6 視点 3D）は著者連絡が必要。

**推奨手順（フェーズ 3）**:
1. データ: 指導現場の動画からフレーム抽出（0.5-1 s 間隔、SL/GS/SG/DH・正面/背面/側面/斜め・晴/曇/雪煙を均等に）。目標 2,000 枚から。
2. アノテーション: CVAT か Label Studio。板は tip/binding 前/binding 後/tail の 4 点＋可視フラグ、ブーツは 1 点（または小 OBB）、ストック 2 点。Ski2DPose が入手できれば形式を合わせて併用。
3. 学習: 手元 GPU がなければ Colab 等で RTMPose-m（Halpe26）をカスタム keypoint 定義で fine-tune（MMPose の `dataset_info` を拡張）。Apache 2.0 で公開サイトと相性が良い。
4. 変換: MMDeploy で ONNX（固定入力 256×192、opset はコミュニティ事例で WebGPU 向けに 12 推奨）。fp16 化でサイズ半減。
5. 組み込み: ONNX を同リポジトリに置き（100 MB 制限内）、onnxruntime-web で推論。前処理（アフィン切り出し）・後処理（SimCC のデコード）を JS で実装。検出器と姿勢モデルを別ファイルにし、片方だけ差し替えられるようにする。
6. 評価: 別日の動画を検証用に取り分け、PCK と「未検出を未検出と言えた率」を指標にする。

## 6. 段階的な改修計画

### フェーズ 1: 現在の構成（MediaPipe、HTML 1 枚）のまま直す
- 撮影方向（側面 / 正面 / 背面 / 斜め）の選択を必須にし、§5 で○△の指標だけ表示。×は項目ごと消す。
- 指標をすべて 2D 画像座標ベースに作り直し、cm を廃止して角度・比率に統一。「エッジ角」を改名。
- 鉛直基準を「雪面の線 2 点タップ」または「ゲート/ストックの鉛直 2 点タップ」で入力。
- `runningMode:'VIDEO'`＋タイムスタンプ、モデル URL のバージョン固定、tasks-vision 更新。
- `requestVideoFrameCallback` で実フレーム時刻を記録、シークタイムアウト時は取得失敗扱い。
- 関節ごとの visibility を指標の採否に使い、信頼度（高/中/低）を数値の横に表示。
- 左右入替検査（前コマとの距離比較）とフラグ表示。ターン判定を画像上の移動＋内傾線符号＋ヒステリシスに変更し、手動上書きを可能に。
- 補間は破線描画のみ、指標は null。平滑化は検出コマのみで One Euro / Savitzky-Golay。
- 板は検出線の実測両端だけ描き、未検出コマは線も値も出さない。
- 期待できる改善: 誤った確信（cm・エッジ角・反転した外脚/内脚）が消え、同一選手の時系列比較と左右ターン比較は実用レベルに近づく。限界: 遠い選手・雪煙・深い内傾での欠落率は変わらない。板検出は依然として古典 CV。

### フェーズ 2: 新しいモデルの組み込み（onnxruntime-web）
- RTMDet-nano（人物）→ 簡易追跡 → RTMPose-m Halpe26（fp16 ONNX、同リポジトリ配置）。MediaPipe は WebGPU/WASM 非対応端末のフォールバックとして残す。
- 切り出しはアスペクト比を保ったアフィン変換、出力は関節ごとの信頼度付き。トップダウン化で遠い選手の分解能が上がる。
- 追跡 ID をユーザーのタップで固定し、複数人（コーチ・前走）を排除。
- 期待できる改善: 2D 関節精度と欠落時の「欠落と言える率」が上がる。足先・踵（Halpe26）で板の基準点が改善。限界: 3D 指標は得られない（意図どおり）。iOS の WebGPU 可否と WASM 速度は実機検証が必要。板・ブーツは未解決。

### フェーズ 3: スキー専用モデルの学習
- 現場動画 2,000 枚から開始して身体＋板 4 点＋ブーツ＋ストックのキーポイントを付け、RTMPose-m を fine-tune（Apache 2.0 系で統一）。可能なら Ski2DPose を併用。
- 板は「可視フラグ付きキーポイント」で学習し、見えないコマには描かない設計を学習段階から入れる。
- 期待できる改善: 板の向き・両端・ブーツ位置が骨格と同じ座標系で安定し、板の開き・tip lead・足元に対する重心投影が条件付きで使えるようになる。限界: 実エッジ角・荷重配分・足圧・3D 前後バランスは依然として映像からは測れない。これらを数値化するには圧力インソール・IMU 等の計測器との併用が必要で、映像解析はその「見える部分」の裏付けに留まる。

## 7. 実施状況（2026-11-01 の全面改修で対応したもの）

§2 の問題番号に対応させて記載する。「対応」は本リポジトリの `ski-posture.html` に実装済み、「一部」は方針の一部のみ、「未対応」はフェーズ 2・3 に持ち越し。

| 順 | 状況 | 実装内容 |
|---|---|---|
| 1 | 対応 | 指標を 2D 画像座標ベースに作り直した（`computeMetrics`）。撮影方向（自動判定＋手動選択）ごとに 観測 / 推定 / 不可 を割り当て、3D（world）は「推定」バッジ付きの参考値に限定。 |
| 2 | 対応 | cm 表示を全廃。位置系は身長比（%）、傾き系は角度。 |
| 3 | 対応 | 「エッジ角」を削除。実エッジ角・荷重配分・足圧・3D 前後バランスは「測定不可」として表示しない旨を画面内の分類表に明記。 |
| 4 | 一部 | 閾値を 12°/s に引き上げ、0.3 秒未満のちらつきを除去、ターン局面（前半/中盤/後半）を追加し、すべて「推定」と明示。画像上の移動を使う判定と手動上書きは未対応。 |

| 7 | 対応 | 板は映像から検出できたコマだけ、実測した両端の長さで描く。足首位置からの板の推定・固定長の線・3D の板の向きは廃止。未検出コマは値も「不可」。 |
| 8 | 一部 | 検出の採否を厳格化（線に沿ったエッジの裏付け率、両側への伸長、信頼度 0.55 未満は未検出）。左右の窓が同じ板を拾った場合は 1 本として扱い「板の開き」を出さない。専用検出器（§4）は未対応。 |

| 11 | 未対応 | 切り出し追跡のため IMAGE モードのまま。モデル URL の固定、tasks-vision の更新も未対応。 |
