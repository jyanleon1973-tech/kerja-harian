## 1. 現在のシステム構成

| 項目 | 現状 |
|---|---|
| 配信 | GitHub Pages（静的ファイルのみ）。`index.html` は別用途（作業日報アプリ、Firebase）で、解析アプリは `ski-posture.html` 1 ファイル |
| フロントエンド | HTML + ES Modules。外部依存は MediaPipe Tasks Vision 0.10.14（CDN）と three.js（ベクトル演算のみ） |
| バックエンド | なし。すべてブラウザ内で処理（動画は端末外に出ない） |
| DB / ストレージ | なし。結果は JSON / CSV の手動保存のみ。Supabase・Vercel は使っていない |
| 姿勢推定 | MediaPipe BlazePose GHUM（`pose_landmarker_{lite,full,heavy}.task`、既定 heavy）。IMAGE モードで 1 コマずつ、前コマ周辺の正方形切り出しを 512px に拡大して検出。見失い時はタイル探索 |
| 板検出 | 足元の小窓に対する古典的画像処理（勾配方向ヒストグラム → 線の裏付け率 → 暗部の連続長）。信頼度 0.55 未満は未検出 |
| 時系列処理 | 左右入替検査（前コマとの距離比較）、1 コマ外れ値の補修、One Euro（前後方向平均）、最大 0.4 秒の線形補間（補間フラグ付き） |
| 指標 | 撮影方向（側面/正面/背面/斜め）ごとに 2D 観測 / 3D 推定 / 不可 を分類。関節ごとの確からしさで採否 |
| ターン判定 | 3D 推定の骨盤向きの回り方（12°/s 以上、0.3 秒未満のちらつき除去）のみ |
| 動画同期 | `video.currentTime` を解析時刻に設定して `seeked` 後に検出。実フレームの提示時刻（mediaTime）は記録していない |
| 書き出し | 骨格・数値を焼き込んだ mp4/webm（MediaRecorder）、CSV、JSON |

## 2. 使用中の姿勢推定モデル

MediaPipe Pose Landmarker（BlazePose GHUM 3D）。入力は人物周辺の切り出し 256×256（モデル内部）。出力は 33 点の 2D 正規化座標 + 可視度と、腰中点原点・体型正規化された 3D「world」座標。単眼回帰のため奥行きは推定であり、スケールは実寸ではない。

## 3. 骨格検出の精度が低い原因

1. **モデルの前提とスキー姿勢の乖離**。BlazePose は直立〜フィットネス姿勢中心の学習で、深い内傾・クローチング・腕とストックの重なりでは関節が体から外れる。トップダウン（人物検出 → 姿勢推定）の高精度モデル（RTMPose / ViTPose）と比べ、COCO 系ベンチマークで AP が大きく劣る（監査 §3）。
2. **入力解像度**。人物が画面の 1/5 以下だと、切り出し拡大をしても実効解像度が足りず関節が揺れる。切り出し追跡（現行）で改善したが限界がある。
3. **毎コマ独立検出**。IMAGE モードのためモデル内部の時系列追跡が使われず、ジッタが出る。後処理（One Euro、外れ値補修）で抑えているが、根本は検出器の安定性。
4. **左右の取り違え**。側面・背面で左右ラベルが入れ替わる。現行の前コマ比較で多くは直るが、長い欠落後や 2 人が重なる場面では検出できない。
5. **検出失敗の扱い**。欠落は最大 0.4 秒補間し補間フラグを付けるが、補間コマの指標は確からしさを下げるだけで null にはしていない。

## 4. スキー板検出の精度が低い原因

1. **専用モデルがない**。古典的なエッジ方向検出のため、白い板、ゲート、影、シュプール、雪煙、ネットに線を取られる。
2. **足元基準の探索**。足首・かかと・つま先の推定位置を窓の中心にしているので、骨格がずれると板の探索窓もずれる。
3. **トップ・テール・ビンディングを区別できない**。線の両端の「暗部の連続長」で見かけの長さを測るだけで、先端の反りや雪に埋まった部分は測れない。
4. **3D の向きは測れない**。側面の映像では、板がどの水平方向を向いても画面上は水平線に近く、原理的に向きが決まらない（現行版はこのため板の 3D 向きを廃止し、画像上の角度と左右の板の相対角のみを出している）。

## 5. 重心計算の問題点

1. 人体部位の質量比（de Leva 1996、成人男性）を 2D 画像座標に適用した「姿勢重心の推定」で、ブーツ・板の重さは含まない。女性・ジュニアの係数はない。
2. 2D 投影のため、斜め撮影では奥行きが混ざる。現行版は側面で前後、正面・背面で左右のみを出し、身長比（%）で表示する（cm 断定は廃止済み）。
3. 足圧中心・荷重配分は映像から測れない（表示しない）。撮影角度の影響（俯角・斜度）は手動スライダー補正のみで、再現性がない。
4. 平滑化・補間を経た座標から計算しているため、補間区間では重心も補間値になる（フラグは付くが数値は出る）。

## 6. サーバー AI 方式への移行計画

```
[ブラウザ: 既存 ski-posture.html]
   ├ 動画選択 → 署名付き URL でオブジェクトストレージへ直接アップロード
   ├ POST /api/analysis/jobs → ジョブ ID
   ├ GET /api/analysis/jobs/{id}（進捗ポーリング）
   ├ GET .../results, .../frames → 既存の表示コード（骨格・板・数値・グラフ・ターン表）で描画
   ├ PATCH .../corrections（手動修正の保存）
   └ POST .../exports（骨格入り動画の生成ジョブ）
[API サーバー: Python + FastAPI]  ジョブ管理、DB（SQLite → Postgres）、ストレージ抽象（ローカル → S3 互換）
[GPU ワーカー: ジョブ実行時のみ起動]
   decode → person detect → track → pose → ski/boot detect → temporal → camera/view → turns → metrics → confidence → save
   各段階の出力を段階別 JSON として保存（誤差の発生箇所を追跡可能）
```

- 既存のブラウザ内解析は「オフライン/簡易モード」として残し、同じ結果スキーマを使う。
- サーバー側のパイプラインは **CPU の MediaPipe バックエンドでも完走**できるようにし（この環境で回帰テストを回すため）、GPU モデルはバックエンド差し替えで導入する。
- 段階ごとに `stage_outputs/{stage}.json` を保存し、モデル名・バージョン・パラメータを `model_versions` に記録して再現性を確保する。

## 7. 推奨する GPU クラウド

ジョブ実行時のみ GPU を使い常時稼働を避ける前提で、**Modal（第一候補）または RunPod Serverless（第二候補）** を推奨する。理由と料金は `docs/phase1-cloud-and-models.md` を参照（料金は確認日・出典付き。未確認項目は未確認と明記）。AWS / GCP の GPU インスタンスは常時稼働か自前のオートスケールが必要で、月 100〜1,000 本の規模では保守コストが見合わない。

**承認待ち**: 有料リソースの作成（アカウント作成、デプロイ、課金開始）は行っていない。Phase 2 の基盤はローカル CPU で完結し、GPU は構成と費用の承認後に接続する。

## 8. 推奨 AI モデル

| 役割 | 第一候補 | 代替 | 備考 |
|---|---|---|---|
| 人物検出 | RTMDet（Apache 2.0） | YOLOX（Apache 2.0） | Ultralytics YOLO は AGPL-3.0 のため商用配布に注意 |
| 追跡 | ByteTrack 系の IoU 追跡 + タップで対象固定 | — | 複数人（コーチ・前走）の排除 |
| 姿勢推定 | RTMPose-m / l（Halpe26 または COCO-WholeBody、ONNX） | ViTPose-B/L | 2D のみ。3D は出さない設計に合う。足先・かかと点（Halpe26）が板の基準に有用 |
| 板・ブーツ検出 | 既製なし → スキー専用データで YOLO 系 / RTMDet のキーポイント or セグメンテーションを fine-tune | 当面は古典 CV（信頼度付き） | 可視フラグ付きで学習し、見えないコマには描かない |
| 動画生成 | FFmpeg + OpenCV 描画 | — | |
| 簡易/フォールバック | MediaPipe Pose（CPU、現行） | — | 回帰テストとオフライン用 |

モデルの選定は名前だけで決めず、**Phase 3 で実際のスキー動画の検証セット**（Phase 2 で作る検証データ作成機能で用意）に対して PCK・関節誤差・左右正解率・検出不能率を比較して決める。

## 9. 月額費用の概算

前提と確認日付きの数値は `docs/phase1-cloud-and-models.md` に記載。要点:
- GPU 処理時間は公開ベンチマークからの**推測値**で、この環境では実測できていない。Phase 2 の基盤ができた後、GPU 接続の承認を得て 1 分動画で実測する。
- 月 100 本では GPU 費用よりストレージ・固定費（DB・API ホスティング）が支配的になりやすい。月 1,000 本では GPU 費用が主になる。

## 10. 開発の優先順位

1. **Phase 2（本セッションで着手）**: FastAPI + ジョブ管理 + ストレージ抽象 + 段階別パイプライン（CPU で完走）+ 既存フロントエンドのサーバー接続 + 回帰テスト + 検証データ作成機能。
2. **Phase 3**: 検証セットを作ってから RTMPose / ViTPose を比較（GPU 承認後）。
3. **Phase 4**: 板・ブーツ検出のデータ作成と fine-tune。手動修正データを（許可のある動画だけ）教師データ形式で蓄積。
4. **Phase 5**: ターン判定の多手掛かり化（板の向き変化、移動軌跡、骨盤、傾斜変化、カメラ動作補正）、重心・バランスの信頼度表示。
5. **Phase 6**: 手動修正 UI（関節ドラッグ、板の両端、左右入替、ターン修正）。
6. **Phase 7**: 実映像での総合検証と回帰。
